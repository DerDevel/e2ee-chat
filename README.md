# 🔒 E2E Encrypted Console Chat

Консольный чат на Go со сквозным шифрованием (End-to-End Encryption).
Сервер выполняет роль сигнального узла и слепого ретранслятора — он **не имеет доступа**
к содержимому сообщений и не раскрывает IP-адреса собеседников друг другу.

## ✨ Возможности

| Возможность | Описание |
|---|---|
| **Сквозное шифрование** | X25519 (ECDH) + ChaCha20-Poly1305 (AEAD) |
| **Прокси-сервер** | IP-адреса клиентов не передаются друг другу |
| **Никнеймы** | Передаются только внутри зашифрованного канала |
| **Одноразовые комнаты** | Кодовое слово живёт в Redis 5 минут и удаляется после pairing |
| **Красивый TUI** | Интерфейс на Bubbletea + Lipgloss |
| **Звуковые уведомления** | ASCII Bell (`\a`) при новом сообщении |
| **Без истории** | Сообщения существуют только в оперативной памяти |
| **Подтверждение подключения** | Получатель вручную подтверждает входящий запрос |

## 🏗 Архитектура

```
┌─────────────┐        gRPC stream         ┌─────────────────────────┐        gRPC stream         ┌─────────────┐
│  Client A   │ ◄────────────────────────► │ Signaling / Relay Server│ ◄────────────────────────► │  Client B   │
│  (Alice)    │                            │                         │                            │   (Bob)     │
└─────────────┘                            └───────────┬─────────────┘                            └─────────────┘
                                                       │
                                                       │ (только при сигналинге)
                                                       ▼
                                              ┌────────────────┐
                                              │     Redis      │
                                              │ keyword → id|pk│
                                              │    TTL 5 min   │
                                              └────────────────┘
```

**Компоненты:**

1. **Signaling / Relay Server** — точка встречи. Регистрирует комнаты, сводит пары,
   релеит зашифрованные байты между двумя сессиями. Никогда не видит plaintext.
2. **Redis** — краткосрочное key-value хранилище. Хранит только временные метки:
   `room:<keyword> → <session_id>|<X25519_pubkey>`. Запись удаляется сразу после pairing.
3. **Client** — консольное приложение. Генерирует ключи, согласовывает секрет,
   шифрует и расшифровывает сообщения локально.

## 🔄 Как это работает

### Жизненный цикл соединения

1. **Запуск клиента A**
   - Генерируется пара ключей X25519.
   - Клиент подключается к серверу по gRPC (bidirectional stream).
   - Пользователь вводит никнейм `Alice`.
   - Вводит кодовое слово `secret-room-123` (или команду `/create secret-room-123`).

2. **Регистрация комнаты**
   - Клиент A отправляет `RegisterRoom{keyword, pubkey_A}`.
   - Сервер делает `SETNX room:secret-room-123 <session_id_A>|<pubkey_A> EX 300`.
   - Если слово занято — ошибка, комната не создаётся.

3. **Запуск клиента B**
   - Генерирует свои ключи, вводит никнейм `Bob`.
   - Отправляет `/join secret-room-123`.
   - Сервер находит запись в Redis, отправляет владельцу `IncomingConnectionRequest`.

4. **Подтверждение**
   - У Alice в консоли появляется запрос `Разрешить подключение? (y/n)`.
   - Alice нажимает `y`.

5. **Pairing**
   - Сервер связывает `session_id_A ↔ session_id_B` в памяти.
   - Удаляет `room:secret-room-123` из Redis.
   - Отправляет каждой стороне публичный ключ собеседника.

6. **Согласование ключей (E2EE)**
   - Каждый клиент вычисляет `SharedSecret = X25519(my_priv, peer_pub)`.
   - `shared_key = SHA256(SharedSecret)`.
   - Обе стороны автоматически обмениваются никнеймами (зашифрованно).

7. **Чат**
   - Каждое сообщение шифруется `ChaCha20-Poly1305(shared_key, nonce, JSON)`.
   - Сервер видит только `{nonce, ciphertext}` и пересылает второму клиенту.
   - Получатель расшифровывает, отображает и издаёт звук `\a`.

## 🔐 Безопасность

### Что видит сервер

| Данные | Видит? |
|---|---|
| `session_id` клиентов | ✅ (внутренний UUID) |
| Публичные ключи X25519 | ✅ (только при сигналинге) |
| Содержимое сообщений | ❌ (только шифротекст) |
| Никнеймы | ❌ (внутри шифротекста) |
| Общий секрет сессии | ❌ |
| Приватные ключи | ❌ (никогда не покидают память клиента) |
| IP-адреса клиентов | ⚠️ Видит, но **не передаёт** собеседнику |

### Криптографические примитивы

- **Обмен ключами**: X25519 (`golang.org/x/crypto/curve25519`)
- **Симметричное шифрование**: ChaCha20-Poly1305 (`golang.org/x/crypto/chacha20poly1305`)
- **KDF**: SHA-256 от общего секрета
- **Формат полезной нагрузки**: JSON `{nick, text, sys}` внутри AEAD

### Модель угроз

✅ **Защищено:**
- Прослушивание трафика на сервере (видит только шифротекст).
- Подмена сообщений (Poly1305 обнаружит изменение).
- Раскрытие IP друг другу (нет прямого соединения).
- Сохранение истории (всё в RAM).
- MITM со стороны **самого сервера** — сравнение ключей

## 📋 Требования

| Компонент | Минимальная версия | Как установить |
|---|---|---|
| **Go** | 1.21+ | https://go.dev/dl/ |
| **protoc** | 3.20+ | https://github.com/protocolbuffers/protobuf/releases |
| **protoc-gen-go** | latest | `go install google.golang.org/protobuf/cmd/protoc-gen-go@latest` |
| **protoc-gen-go-grpc** | latest | `go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest` |
| **Redis** | 6+ | `docker compose up -d redis` или системный пакет |
| **Docker** (опционально) | 20+ | https://docs.docker.com/get-docker/ |



> 💡 Убедитесь, что `$GOPATH/bin` (обычно `~/go/bin`) в переменной `$PATH`,
> иначе `protoc` не найдёт плагины.
