# 🔒 E2E Encrypted Console Chat

[![CI](https://github.com/DerDevel/e2ee-chat/actions/workflows/ci.yml/badge.svg)](../../actions/workflows/ci.yml)
[![Go Reference](https://pkg.go.dev/badge/github.com/DerDevel/e2ee-chat.svg)](https://pkg.go.dev/github.com/DerDevel/e2ee-chat)
[![Go Report Card](https://goreportcard.com/badge/github.com/DerDevel/e2ee-chat)](https://goreportcard.com/report/github.com/DerDevel/e2ee-chat)
[![License: Apache 2.0](https://img.shields.io/badge/License-Apache_2.0-blue.svg)](LICENSE)

Консольный чат со **сквозным (end-to-end) постквантовым шифрованием**.
Сервер — только сигнальный узел и «слепой» ретранслятор: он **никогда не видит**
содержимое сообщений и никнеймы, не хранит историю и не раскрывает IP-адреса
собеседников друг другу.

- **Гибридное постквантовое согласование ключей**: X25519 (ECDH) + **ML-KEM-768** (FIPS 203)
- **AEAD**: ChaCha20-Poly1305, раздельные ключи на направление, защита от replay
- **Транскрипт-биндинг** рукопожатия в KDF — key-synchronization-атаки рассинхронизируют SAS
- **Код безопасности (SAS)** для обнаружения MITM сверкой вне канала
- **TLS 1.3** с постквантовым key exchange (X25519MLKEM768), pin сертификата или mTLS
- Одноразовые комнаты, TUI на Bubbletea, полная поддержка UTF-8 (кириллица, эмодзи)
- Без истории: сообщения существуют только в RAM обеих сторон

## 🎬 Демо

Два терминала, сервер между ними видит только шифротекст:

```
 ──────────────────────── Терминал 1 (Alice) ────────────────────────   ──────────────────────── Терминал 2 (Bob) ────────────────────────
  🔒 E2E Encrypted Console Chat                                         🔒 E2E Encrypted Console Chat

  Введите никнейм: Alice                                                Введите никнейм: Bob
  Кодовое слово (или /join <слово>, /help): tea-room-77                 Кодовое слово (или /join <слово>, /help): /join tea-room-77

  ⣾ * Ожидание подключения по ключу tea-room-77...                      ⣽ * Поиск комнаты tea-room-77...
  * Входящий запрос на подключение.
  Разрешить подключение? (y/n): y
  * Запрос принят. Установка соединения...
  * Согласование ключей...
  * Код безопасности: 48210 93755 30261                                 * Код безопасности: 48210 93755 30261
  * Сверьте код с собеседником. Несовпадение означает MITM-атаку.      * Сверьте код с собеседником. Несовпадение означает MITM-атаку.
  * Собеседник Bob в сети                                               * Собеседник Alice в сети

  [Alice] > привет, Боб! 👋                                             [Bob]: привет, Боб! 👋
  [Alice]: и тебе привет                                                [Bob] > и тебе привет
```

*Коды безопасности совпали → между Alice и Bob нет MITM.*

## 🚀 Быстрый старт

Понадобятся: **Go 1.26+**, **Redis 6+** (локально или в Docker), **openssl**.
Все команды — из корня репозитория.

```bash
git clone https://github.com/DerDevel/e2ee-chat.git
cd e2ee-chat
```

### 1. Сборка и сертификат

```bash
make build        # соберёт ./server/server и ./client/client
make certs        # создаст dev-сертификат и напечатает E2EE_TLS_PIN
```

### 2. Redis

```bash
export REDIS_PASSWORD="$(openssl rand -hex 24)"
docker compose -f deploy/docker-compose.yml up -d
```

> Без Docker: поднимите свой Redis и задайте `E2EE_REDIS_ADDR`/`E2EE_REDIS_PASSWORD` на шаге 3.

### 3. Сервер (терминал 1)

```bash
export E2EE_REDIS_PASSWORD="$REDIS_PASSWORD"
./server/server          # слушает :50051, TLS 1.3
```

### 4. Два клиента (терминалы 2 и 3)

```bash
# терминал 2 — создает комнату
./client/client -pin <пин из шага 1>

# терминал 3 — подключается к удаленному серверу той же командой:
# ./client/client -addr chat.example.com:50051 -pin <пин>
./client/client -pin <пин из шага 1>
```

Дальше: никнеймы → первый клиент вводит кодовое слово, второй — `/join <слово>`
→ подтвердить (`y`) → **сверить код безопасности по другому каналу** (голос,
лично) → общаться.

> ⚠️ Никогда не используйте `E2EE_TLS_INSECURE=1` вне локальной разработки.

## 📱 Использование

### Сценарий

1. **Создать комнату**: ввести кодовое слово (3–64 символа: `a-z A-Z 0-9 . _ -`) —
   комната живёт 5 минут и исчезает после пейринга. Используйте длинные
   случайные слова — короткие можно перебрать.
2. **Подключиться**: `/join <слово>` — владелец увидит запрос и подтвердит (`y`/`n`).
3. **Сверить SAS**: обе стороны показывают 15-значный код. Совпал — MITM нет.
4. **Общаться**: всё, что вы видите как `[Ник]`, пришло зашифрованным.
5. **Собеседник ушёл?** Введите новое кодовое слово прямо в том же клиенте —
   ключи автоматически сгенерируются заново.

### Команды клиента

| Команда | Где работает | Действие |
|---|---|---|
| `/join <слово>` | экран кодового слова | Подключиться к комнате |
| `/nick <имя>` | чат | Сменить никнейм |
| `/help` | везде | Справка |
| `/quit` | везде | Выход (также `Ctrl+C`) |

Лимиты: сообщение до 2000 символов, ник до 32; звук `🔔` (ASCII bell) при
новом сообщении.

## 🏗 Архитектура

```
┌─────────────┐        gRPC / TLS 1.3        ┌─────────────────────────┐        gRPC / TLS 1.3        ┌─────────────┐
│  Client A   │ ◄───────────────────────────► │ Signaling / Relay Server│ ◄───────────────────────────► │  Client B   │
│  (Alice)    │      только шифротекст        │  «слепой» ретранслятор  │      только шифротекст        │   (Bob)     │
└─────────────┘                               └───────────┬─────────────┘                               └─────────────┘
                                                          │ только при сигналинге
                                                          ▼
                                                 ┌────────────────┐
                                                 │     Redis      │
                                                 │ keyword → keys │
                                                 │   TTL 5 min    │
                                                 └────────────────┘
```

**Компоненты**

| Компонент | Роль |
|---|---|
| **client** | Генерирует ключи, согласует секрет, шифрует/расшифровывает локально. TUI на Bubbletea + Lipgloss |
| **server** | Сводит пары по кодовому слову, релеит непрозрачные байты. Rate-limit сигналинга (1 req / 2 c) и чата (~30 msg/s), лимиты соединений (1024 глобально / 64 на IP) |
| **Redis** | Эфемерное хранилище комнат без персистентности; запись удаляется сразу после пейринга |

## 🔄 Протокол

1. **Регистрация** — клиент A публикует `keyword + X25519 pubkey + ML-KEM-768 pubkey`
   (`SETNX`, TTL 5 мин, атомарный claim).
2. **Поиск** — клиент B шлёт `/join`; сервер пересылает запрос владельцу.
3. **Подтверждение** — владелец явно соглашается (`y`).
4. **Pairing** — сервер связывает сессии, удаляет комнату, раздаёт сторонам
   публичные ключи друг друга.
5. **Гибридное согласование** — обе стороны считают `X25519(my_priv, peer_pub)`;
   сторона с меньшим X25519-ключом инкапсулирует ML-KEM и пересылает ciphertext
   (1088 байт) через релей. Из `X25519-секрет ‖ KEM-секрет` через HKDF-SHA256
   выводятся **два направленных ключа** и SAS. В соль HKDF замешан весь
   транскрипт (все четыре публичных ключа + KEM ciphertext).
6. **Чат** — каждое сообщение: `ChaCha20-Poly1305(send_key, counter_nonce, {nick, text})`;
   сервер видит только `{nonce, ciphertext}`. Получатель отвергает повторы
   счётчика и все, что пришло не по порядку.
7. **Разрыв** — любая сторона отключается: вторая возвращается к вводу кодового
   слова, история TUI затирается, следующий пейринг — со свежими ключами.

## 🔐 Безопасность

### Что видит сервер

| Данные | Видит? |
|---|---|
| Публичные ключи (только при сигналинге) | ✅ |
| `session_id` (внутренний UUID из crypto/rand) | ✅ |
| Содержимое сообщений / никнеймы / общий секрет | ❌ |
| Приватные ключи | ❌ никогда не покидают клиент |
| IP собеседника | ⚠️ видит, но **не передаёт** |

### Криптографическая основа

| Примитив | Выбор |
|---|---|
| Обмен ключами | X25519 + ML-KEM-768 (гибрид: секрет цел, пока цела хотя бы одна из примитивов) |
| KDF | HKDF-SHA256 (RFC 5869), **salt = весь транскрипт рукопожатия** — защита от key-synchronization-атак |
| Шифрование | ChaCha20-Poly1305, два раздельных ключа на направление |
| Nonce | Монотонный счётчик + отвержение повторов и out-of-order |
| MITM-детектор | SAS: 15 цифр (~50 бит), сверяется вне канала |
| Транспорт | TLS 1.3 only, X25519MLKEM768, аутентификация CA или pin |
| Санитизация | Весь удалённый текст чистится от ANSI/ESC, C0/C1, BiDi, zero-width до рендера |

### Модель угроз

**Защищено:** пассивное прослушивание; подмена/повтор сообщений (AEAD + счётчики);
раскрытие IP; сохранение истории; MITM через сигналинг (транскрипт-биндинг
гарантированно рассинхронизирует SAS при любой подмене ключей); флуд со стороны
собеседника и сервера (rate-limits); перебор комнат; терминальные инъекции через
ник/текст/ошибки; исчерпание памяти сервера массовыми подключениями.

**Остается на пользователе:** сверить SAS целиком (система обнаруживает MITM,
только если коды сравнили); выбрать кодовое слово с высокой энтропией.

Политика сообщений об уязвимостях: [SECURITY.md](SECURITY.md).

## 🖥 Продакшен-чеклист

- [ ] Сертификат от настоящего CA (Let's Encrypt) → клиенту `E2EE_TLS_CA=ca.crt`
      вместо pin; или оставьте pin — он не хуже для single-server
- [ ] **mTLS**: `E2EE_TLS_CLIENT_CA=client-ca.crt` — только клиенты с клиентским
      сертификатом смогут подключиться
- [ ] Redis с паролем, доступен только с localhost/приватной сети
- [ ] Один экземпляр сервера: карты пейринга живут в памяти процесса
      (масштабирование за общим Redis пока не поддерживается — см. [FAQ](#-faq))
- [ ] Ограничьте `E2EE_LISTEN` фаерволом; перед сервером прокси не нужен

## ⚙️ Конфигурация

Всё настраивается флагами командной строки **или** переменными окружения
(флаг имеет приоритет). Полный список — `-h` у любого из бинарей.

### Сервер

| Флаг | Переменная | По умолчанию | Описание |
|---|---|---|---|
| `-listen` | `E2EE_LISTEN` | `:50051` | Адрес прослушивания |
| `-redis-addr` | `E2EE_REDIS_ADDR` | `127.0.0.1:6379` | Адрес Redis |
| `-redis-password` | `E2EE_REDIS_PASSWORD` | — | Пароль Redis |
| `-redis-db` | `E2EE_REDIS_DB` | `0` | Номер БД Redis |
| `-tls-cert` | `E2EE_TLS_CERT` | `server.crt` | Сертификат TLS |
| `-tls-key` | `E2EE_TLS_KEY` | `server.key` | Приватный ключ TLS |
| `-tls-client-ca` | `E2EE_TLS_CLIENT_CA` | — | CA-бандл клиентов для mTLS |

### Клиент

| Флаг | Переменная | По умолчанию | Описание |
|---|---|---|---|
| `-addr` | `E2EE_SERVER_ADDR` | `localhost:50051` | **Адрес сервера для соединения** |
| `-server-name` | `E2EE_TLS_SERVER_NAME` | host из `-addr` | Ожидаемое имя в сертификате |
| `-ca` | `E2EE_TLS_CA` | системные корни | PEM-бандл доверенного CA |
| `-pin` | `E2EE_TLS_PIN` | — | SHA-256 pin сертификата (для self-signed) |
| `-insecure` | `E2EE_TLS_INSECURE=1` | выкл | Отключить проверку TLS. **Только локальная разработка** |

Примеры:

```bash
# подключиться к удаленному серверу с доверенным CA (Let's Encrypt и т.п.)
./client/client -addr chat.example.com:50051

# self-signed сервер — по pin (см. make certs)
./client/client -addr 203.0.113.7:50051 -pin 91c0ac3e...

# то же через переменные окружения (удобно в .env / CI)
E2EE_SERVER_ADDR=chat.example.com:50051 ./client/client
```

Шаблон `.env` — в [`.env.example`](.env.example).

  пейринг** после ухода собеседника.

## ❓ FAQ

**Почему SAS именно 15 цифр?**
~50 бит: перебор безнадёжен, а целиком сверить 15 цифр реально. Более длинные
коды пользователи сравнивают по префиксу — и этим обесценивают свою же защиту.

**Почему нельзя «просто довериться» TLS и не сверять SAS?**
TLS защищает канал клиент↔сервер, но сам сервер — участник, которому мы не
доверяем содержимое. SAS — единственный способ убедиться, что между вами нет
второй пары рук, подменяющей ключи.

**Сервер обязательно с Redis?**
Да, Redis — часть дизайна сигналинга (атомарный claim комнат с TTL). Для
продакшена достаточно одного инстанса Redis без персистентности.

**Можно запустить несколько серверов за балансировщиком?**
Пока нет: соответствие «комната → живая сессия» хранится в памяти процесса.
Общий Redis синхронизирует только комнаты, но не пейринги.

**Кодовое слово видно серверу? Кто-то может занять мою комнату?**
Видно, и комнату можно перебрать — поэтому выбирайте длинные случайные слова
(например, 4–5 слов из словаря). Перебор дополнительно удорожается rate-limit'ом
сигналинга.

**Где хранится история?**
Нигде. Ни на сервере, ни в Redis, ни на диске клиентов — только в RAM активного
TUI (максимум 500 последних строк), и она затирается при разрыве.
